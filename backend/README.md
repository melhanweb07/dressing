# Aavya Studio REST API

Independent Express 5 + TypeScript API backed by Supabase Auth, PostgreSQL, and Storage. Guest checkout is supported; customer accounts are optional. No payment gateway is integrated. Payments start as `Pending` and only an authenticated administrator can mark them `Verified`.

## Requirements and local setup

- Node.js 20.19+ or 22.12+
- A Supabase project

From this directory:

```powershell
npm install
Copy-Item .env.example .env
# Fill in the Supabase project URL, anon key, and server-only service role key.
npm run dev
```

The API listens on `http://localhost:5000/api`; `GET /api/health` checks readiness. Use `npm run build`, `npm start`, `npm test`, or `npm run typecheck` for production builds and checks.

The Supabase service-role key is used only by the backend and bypasses RLS. Keep `.env` out of version control and configure the key in the backend deployment's secret manager. Never use it in a `VITE_*` variable or browser bundle.

## Supabase setup

1. Apply the migrations in `supabase/migrations/` to the project using the Supabase CLI (`supabase db push`) or run both files in lexical order in the SQL editor.
2. The migrations create the normalized schema, RLS policies, four public image buckets, and transactional order RPCs. See [`DATABASE.md`](DATABASE.md) for the ER diagram, table/policy reference, seed instructions, and storage setup.
3. Invite/create the first admin user using Supabase's dashboard or another trusted administrative process. There is deliberately no public registration endpoint.
4. Promote only that trusted user by setting the profile role using its Auth user UUID in the SQL editor:

   ```sql
   update public.profiles set role = 'admin'
   where id = 'REPLACE-WITH-TRUSTED-AUTH-USER-UUID';
   ```

   The auth trigger always creates new users with the `customer` role, ignoring user-supplied metadata.
5. Configure the shop's public contact details, GPay number, delivery settings, and policies in `public.store_settings` (row id `main`) or with `PUT /api/admin/settings`.
6. Add categories and products through the admin API. Image uploads are limited to JPEG, PNG, or WebP; upload paths are generated by the server.

## API conventions

All responses use this envelope:

```json
{ "success": true, "message": "Product fetched successfully.", "data": {} }
```

Failures use `{ "success": false, "message": "...", "errors": [] }`. Collection endpoints return pagination metadata inside `data`, for example `{ "items": [], "page": 1, "limit": 24, "total": 0, "pages": 0 }`. Search and filter values are validated with Zod; pagination limits are capped.

### Public endpoints

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/health` | Health check |
| `GET` | `/api/products` | Active products; supports `search`, `category` (slug or name), `minPrice`, `maxPrice`, `size`, `color`, `sort`, `page`, `limit` |
| `GET` | `/api/products/:id` | Active product by UUID |
| `GET` | `/api/categories` | Visible categories |
| `GET` | `/api/categories/:id` | Category details |
| `GET` | `/api/settings` or `/api/store/settings` | Safe public shop settings |
| `POST` | `/api/orders` | Guest or customer order; server recalculates price, discount and delivery, locks stock, and creates a pending-payment order |
| `GET` | `/api/orders/track?orderId=...&phone=...` | Track by order reference and matching phone |
| `GET` | `/api/orders/:id?phone=...` | Same phone-verified order lookup |
| `GET`, `POST`, `DELETE` | `/api/wishlist[/:productId]` | Customer-authenticated wishlist; guest wishlist remains client-side |

Order input accepts customer delivery details, product UUID, selected size/colour, and quantity only. Client-submitted prices, stock, subtotal, delivery, and totals are not accepted as authoritative or persisted.

### Authentication and protected admin endpoints

Send `Authorization: Bearer <Supabase access token>`. Every protected request validates the token with Supabase Auth, then fetches the role from `public.profiles`. Admin claims or roles sent in request data are never trusted.

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/auth/admin/login` | Supabase Auth email/password login; denies non-admin profiles |
| `POST` | `/api/auth/refresh` | Refresh Supabase access token and re-check admin role |
| `GET` | `/api/auth/session` | Validate token and current database role |
| `POST` | `/api/auth/logout` | Revoke the Supabase session |
| `GET` | `/api/admin/overview` | Store metrics and recent orders |
| `GET` | `/api/admin/orders` | Search/filter/paginated full order list |
| `GET` | `/api/admin/orders/:id` | Full customer/order details |
| `GET` | `/api/admin/orders/:id/history` | Order, payment, and admin-note change history |
| `PATCH` | `/api/admin/orders/:id` | Update status, payment status, and/or admin notes |
| `PATCH` | `/api/admin/orders/:id/status` | Update order status; cancellation restores inventory atomically |
| `PATCH` | `/api/admin/orders/:id/payment` | Manually set `Pending`, `Payment Reported`, `Verified`, `Failed`, or `Refunded` |
| `PATCH` | `/api/admin/orders/:id/notes` | Update private admin notes |
| `GET`, `POST`, `PUT`, `PATCH`, `DELETE` | `/api/admin/products[/:id]` | Product management; deletion archives products |
| `POST`, `PUT`, `PATCH`, `DELETE` | `/api/products[/:id]` | Equivalent admin-only product write endpoints |
| `GET`, `POST`, `PUT`, `PATCH`, `DELETE` | `/api/admin/categories[/:id]` | Category management |
| `POST`, `PUT`, `PATCH`, `DELETE` | `/api/categories[/:id]` | Equivalent admin-only category write endpoints |
| `PUT`, `PATCH` | `/api/admin/settings` | Update public store settings |
| `POST`, `DELETE` | `/api/admin/uploads` | Upload/delete generated public image assets |

Payment verification is always a manual admin action after checking the actual GPay transaction. A customer request, screenshot, or payment-method selection never changes payment status to `Verified`. COD can be enabled in store settings and remains pending until explicitly checked/updated.

## Transaction and inventory model

`create_store_order` is a PostgreSQL `SECURITY DEFINER` RPC callable only with the service role. It reads current product/settings values, locks each product row `FOR UPDATE`, checks active/variant/stock constraints, applies current discount prices and delivery settings, inserts the order/items, and decrements stock inside one transaction. Competing checkouts cannot oversell. `set_order_status` locks the order and restores product stock once on cancellation; cancelled/delivered orders cannot be improperly reopened/cancelled. The `order_history` trigger records status, payment, and note changes.

Size/colour combinations are represented by `product_variants`; checkout locks and decrements that row when a variant exists. Variant changes recalculate the API-compatible aggregate `products.stock`. If no variants exist, the RPC retains the legacy product-level inventory behavior. Variant stock is managed through trusted administrative database operations; the current product API does not expose a variant-specific inventory editor.

## Frontend integration

Set the React app's `VITE_API_URL` to the deployed API base path, for example `https://api.example.com/api`. The frontend Axios client unwraps the standard success envelope and normalizes paginated product/order collections. `src/lib/apiServices.ts` contains client methods for products, categories, orders, wishlist, store settings, and image uploads.

## Tests and API examples

- `npm test` runs Supertest API validation/auth/health tests and image magic-byte tests without connecting to a real Supabase project.
- `npm run build` type-checks and compiles the service.
- Import `postman/Aavya-Store-API.postman_collection.json` in Postman; set the base URL and a valid admin token after login.

## Deployment

Deploy this directory as its own Node.js service (Render, Railway, Fly.io, or another Node host): install with `npm ci`, build with `npm run build`, and start with `npm start`. Configure all environment values in the host's secret/config settings; set `FRONTEND_ORIGINS` to the exact deployed frontend origin(s). Apply database migrations before switching the frontend to production API traffic. Keep the frontend Vercel deployment and the backend API deployment independently configured.
